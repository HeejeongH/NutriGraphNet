# Why these G_layers_* folders were quarantined (2026-07-15)

`results/gpu/G_layers_1` through `G_layers_4` showed byte-identical
LightGCN metrics across all four folders (HR@10=0.7208, AUC=0.82181610...,
matching only the num_layers=3 default to 10 decimal places), instead of
the varying values the paper reports (L=1: 0.7456, L=2: 0.7844, L=3: 0.7208,
L=4: 0.7576 — from `results/analysis/G_layers_*`, which is correct and
matches the paper's Table G exactly).

Root cause check (2026-07-15): confirmed the *current* nutrigraphnet_v2.py
correctly threads `--num_layers` through to LightGCN — a local CPU test
(2 epochs, 1 fold) gave HR@10=0.0860 at num_layers=1 vs. HR@10=0.1900 at
num_layers=4, clearly different. So this is NOT a live code bug. These
four folders must have been generated by an older/different code path
(before num_layers was wired through for the lightgcn/ngcf CLI variants,
or some other now-unreproducible environment difference) and were never
cleaned up after `results/analysis/G_layers_*` (the correct data actually
used in the paper) was produced.

Impact: none on the published paper — Section 6.5/Table G was written
from `results/analysis/G_layers_*`, not this folder.

Action taken: moved to `results/gpu/_stale/` (not deleted) so
`generate_summary_gpu.py` / `run_analysis_experiments.py --exp summary`
no longer pick these up when scanning `results/gpu/`. Safe to delete
this whole `_stale/` directory once confirmed unneeded.
